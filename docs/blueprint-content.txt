PART 1. PROJECT CONCEPT
1.1 Project Summary
BonAppé Find is a full-stack restaurant discovery web application built for the 6ADDBASE Final Project: Restaurants. It reads restaurant records from a MongoDB Atlas database named dbRestaurants, displays them in a clean and searchable interface, and lets users add, edit and delete restaurants. What makes it different from a plain listing is that every restaurant and every country carries curated static information: a story, signature dishes, dining etiquette, tipping customs and food festivals. Users learn the culture behind the plate, not only the address.
Item | Detail
Project name | BonAppé Find
Tagline | Great dining starts with a great find.
Project type | Full-stack web application (single-page application with REST API)
Frontend | Reference stack: Vue 3 (Composition API), Vite, Vue Router, Pinia, Axios, plain CSS with design tokens. Any frontend framework that calls the REST API can be used (see Part 6).
Backend | Reference stack: Node.js 20, Express 4, Mongoose 8, express-validator. Any language that implements the API in Part 3.5 can be used (see Part 6).
Database | MongoDB Atlas, database dbRestaurants, collection restaurants (plus countries, guides, faqs, messages, subscribers, reviews, users)
Design | Figma, using the two supplied color palettes (see Part 2)
Course | 6ADDBASE&6WCSERVER, Final Project: Restaurants

1.2 The Concept at a Glance (5W1H)
Question | Short answer
WHO | Food explorers, travelers, students and local diners who want to find restaurants and understand their food culture. Restaurant owners and site admins maintain the data. Built by a four-member student team.
WHAT | A restaurant discovery web app with search by name and cuisine, borough/region filter and group, a Best Quality ranking (aggregate score > 90), full add/edit/delete, restaurant profiles and country food guides.
WHY | Restaurant information is scattered and rarely explains local dining customs. The project also demonstrates CRUD, search, group-by, aggregation and cloud database syncing as required by the course rubric.
WHERE | Used in any modern web browser on desktop, tablet and mobile. Hosted on cloud services with data stored in MongoDB Atlas. Covers New York City boroughs (course dataset) plus eight featured countries.
HOW | Design in Figma, build a REST API on MongoDB, build an interface that consumes the API, enrich with static content, test, document and submit through GitHub and a PDF.

1.4 WHAT
Product definition
BonAppé Find is a responsive single-page web application. The client calls a REST API (Express in the reference stack). The API reads and writes MongoDB Atlas through Mongoose. All pages share one header with navigation and one footer.
Features required by the course (single phase)
Home page with a hero, search box, highlights and links to every main section.
List of restaurants displayed in a table with name, borough, cuisine, address and grades, with pagination.
Search by restaurant name and by cuisine.
Filter / Group by borough or region using filter buttons driven by a MongoDB group-by.
Best Quality page that uses an aggregate to show restaurants whose combined score is greater than 90.
Add, Edit and Delete restaurants, saved to MongoDB Atlas.
Atlas syncing so the data lives in the cloud and every change appears in the Atlas collection.
Static information features (our creative layer)
Restaurant profile pages: tagline, story, signature dishes, price range, opening hours, dress code, reservation advice, dietary options and a fun fact.
Country guides: overview, signature dishes, meal rhythm, dining etiquette, tipping, best season to eat, food festivals, a useful phrase and a fun fact.
Fallback profile text: restaurants imported from the course dataset receive an automatic profile built from their cuisine, borough and country so no page is ever empty.
All other features (same single phase)
Insights dashboard, cuisine explorer, food guides, surprise me, compare restaurants, saved list, reviews, newsletter, contact form, team page, accessibility statement and admin login. These are built together with every feature above in one single phase; there is no separate enhancement stage. The full page list is in Part 4.
1.5 WHY
Problem statements
Restaurant information is spread across maps, social media and review sites, and rarely explains local dining customs.
Travelers and students do not know how to read ratings or compare restaurants by quality in one place.
Small restaurants cannot easily keep a listing up to date.
Solution
One clean web application that stores restaurants in a cloud database, lets people find them quickly, ranks them by quality and explains the food culture of each country, while giving authorized users simple tools to add, edit and delete records.
Measurable objectives
No. | Objective | How we measure it
1 | Display every record in dbRestaurants with pagination | List page loads 20 records per page and total count matches Atlas
2 | Search by name and by cuisine returns results in under one second | Manual timing on the local and deployed app
3 | Add, edit and delete persist in Atlas | Change a record in the app, then confirm it in the Atlas collection view
4 | Aggregate shows only restaurants with a total score greater than 90 | Compare the Best Quality list with an Atlas aggregation run in Compass
5 | Eight country guides and sixteen curated restaurant profiles are available | Count records in countries and curated restaurants
6 | Layout works at 360, 768 and 1280 pixels wide | Browser responsive mode checks recorded in screenshots
7 | All 60 rubric points are addressed | Checklist in Part 8 completed before submission

Academic purpose
The project shows that the team can design a database-backed web application, use MongoDB aggregation and grouping, sync with MongoDB Atlas and document the work professionally.

1.8 Rubric Alignment (60 points)
Rubric criterion | Pts | Where BonAppé Find satisfies it
Aggregate function in the code (highest ratings) | 10 | Best Quality page. Endpoint GET /api/restaurants/stats/top-quality uses $unwind, $group with $sum and $match total greater than 90.
Filter / Group feature | 10 | Borough filter buttons on the list page. Endpoint GET /api/restaurants/stats/by-borough uses $group to count restaurants per borough.
Search feature | 10 | Search box on the list page filters by name or cuisine (query parameters search and field).
Source code | 10 | Complete monorepo on GitHub and the code included in the printed submission.
Web design | 5 | Palette from the brief, Figma designs, responsive layout and consistent components.
Grammar and spelling | 5 | Copy in Part 5 is proofread; final check by Casey Ong before submission.
Atlas syncing | 10 | Database dbRestaurants hosted on MongoDB Atlas; screenshots of the Atlas collection prove syncing.

Design note on scoring: in raw New York inspection data a lower score is better. To match the course rubric, which asks for aggregated scores greater than 90, BonAppé Find defines a Quality Score as the combined total of all score values recorded for a restaurant, and the Best Quality page lists totals above 90. The threshold and sort direction are kept in one configuration constant so the team can adjust them if the instructor prefers a different reading.

2.6 Layout and Accessibility
Container width 1200 px with 24 px side padding; 12-column grid on desktop, 4 columns on mobile.
Breakpoints: 600 px (mobile), 900 px (tablet, header becomes hamburger), 1200 px (desktop).
All images need alt text; interactive elements have a visible focus ring; buttons are at least 44 by 44 px on touch screens.
Table on the list page becomes stacked cards below 600 px.
Never use color alone to show grade or error; always include the letter or an icon and text.
2.7 Logo and Wordmark Rules
The brand name is BonAppé Find. These rules keep the name, the icon and the tagline consistent in Figma, on the website and in print.
Item | Rule
Wordmark | BonAppé Find, set in the heading font. B, A and F are capitals and the é always carries its accent in visible text.
Tagline | Great dining starts with a great find. Set in the body font, italic, below or beside the wordmark.
Icon | A fork whose handle ends in a small magnifying glass. Candle on Forestry, or Forestry on Candle.
Lockup | Icon, wordmark and tagline stacked and centered for the hero, the footer and the title page.
Minimum size | Wordmark no smaller than 96 px wide on screen or 25 mm in print. Icon alone no smaller than 24 px.
Clear space | Keep a gap equal to the height of the letter B on all four sides.
Plain-text name | Use bonappe-find for URLs, file names and the repository, and bonappefind for storage keys and database users. No accent, no spaces.
Favicon | favicon.svg: the icon alone on a Forestry rounded square.
Do not | Stretch or outline the logo, recolor it outside the palette, place a Candle logo on Moss Gardens or Leaf (contrast rule in Section 2.2), or drop the accent in visible text.

3.3 Responsibility of Each Layer
Layer | Responsibility | Must not
routes | Map a URL and HTTP method to validators and a controller | Contain business logic
validators | Check and sanitize input and return clear messages | Query the database
controllers | Handle the request, call Mongoose, send the JSON envelope | Format HTML or hold secrets
models | Define schemas, indexes and small helper methods | Call other controllers
middleware | Errors, authentication, rate limiting and validation results | Hold route-specific logic
services (client) | Send HTTP requests and return data | Change the interface directly
stores (client) | Hold shared state such as filters, saved list and user | Call the DOM
views and components | Display data and capture user actions | Contain API URLs

3.6 Key MongoDB Pipelines
Aggregate: Best Quality (total score greater than 90)
Restaurant.aggregate([
  { $match: filters },                       // optional country or cuisine
  { $unwind: "$grades" },
  { $group: {
      _id: "$_id",
      name: { $first: "$name" },
      borough: { $first: "$borough" },
      cuisine: { $first: "$cuisine" },
      country: { $first: "$country" },
      address: { $first: "$address" },
      totalScore: { $sum: "$grades.score" },
      gradeCount: { $sum: 1 }
  } },
  { $match: { totalScore: { $gt: min } } },  // min defaults to 90
  { $sort: { totalScore: -1, name: 1 } },
  { $limit: limit }
]);
Group: restaurants per borough
Restaurant.aggregate([
  { $match: filters },
  { $group: { _id: "$borough", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
]);

3.8 Setup and MongoDB Atlas Syncing
The commands below are for the reference Node.js stack. If your team uses another language, run the equivalent import and seed scripts for that stack (see Section 6.7 for the JSON seed format).
Create a free MongoDB Atlas account and a cluster (M0 free tier).
Create a database user (Database Access) and allow your IP address (Network Access; use 0.0.0.0/0 only for testing and deployment).
Copy the connection string and place it in server/.env as MONGODB_URI, ending with /dbRestaurants.
Import the course dataset into dbRestaurants, collection restaurants (Atlas Load Sample Data or mongoimport with the provided JSON).
Run the import script: npm run import:db --prefix server. It adds country, countrySlug and city fields to imported records.
Run the seed script: npm run seed --prefix server. It inserts countries, 16 curated restaurants, guides and FAQs.
Start both apps: npm run dev from the repository root. The API runs on port 5000 and the client on port 5173.
Test add, edit and delete in the app, then open Atlas Collections and take a screenshot as proof of syncing.

4.11 Suggested Work Order Inside the Single Phase
Step 1, foundation: roles and RBAC middleware, logout, restaurant status, approval status, soft delete, activity log.

Step 3, profile data: hours and Open Now, price range, dietary tags, amenities, contact and social links, gallery, menu preview.
Step 4, discovery: advanced search, new filters and sorts, URL filters, discovery lists, view counter, similar restaurants, favorites.
Step 5, community: star ratings and breakdown, review reports, moderation queue, suggest an edit, owner replies.

Step 7, polish: skeleton loaders, empty states, dark mode, map view, Swagger documentation, tests.

Hero title: About BonAppé Find

Our story
BonAppé Find began with a simple question: why does a restaurant list tell us where to eat, but never how to enjoy it? A name and an address are useful, yet they leave out the stories that make a meal memorable, such as why a dish is served at a certain time, how to share it, or what is polite when the bill arrives.
Four students taking the 6ADDBASE course decided to answer that question. We started with a database of restaurants and built a web application around it. Then we added something most listings forget: the culture. Every country guide in BonAppé Find explains signature dishes, meal times, etiquette, tipping and festivals, and every curated restaurant has a story and a must-order list.
The result is a guide that works for the quick search ("find me a bakery in Brooklyn") and for the curious traveler ("what should I know before dinner in Tokyo?").
Why the name?
BonAppé Find takes its name from bon appétit, the wish we say before a meal, and from the word find. Great dining starts with a great find, so finding the right place is the first course. After that, the story, the dishes and the table manners make the meal.
Our mission
To help people find good restaurants quickly and to make every table feel welcoming by sharing the food culture behind the plate.
Our vision
A world where nobody feels nervous walking into a restaurant, anywhere, because they already know what to order and what to expect.
What we believe
Value | What it means
Respect | We describe every food culture with care and avoid stereotypes.
Clarity | We show the numbers behind every ranking so you can judge for yourself.
Curiosity | We celebrate regional dishes, street food and family kitchens as much as fine dining.
Ownership | Restaurant data should be easy for the people who know it best to correct and update.

What makes us different
Static, hand-written information for every curated restaurant and every country guide.
A transparent Quality Score built from recorded grades.
Full add, edit and delete tools, not just a read-only list.
A design inspired by dark wood, green glass and warm candlelight.
About our data
Most restaurants in BonAppé Find come from the dbRestaurants dataset provided in our course, which covers New York City boroughs. To show how the app works for the world, we added sixteen curated restaurants across eight countries. These sixteen are fictional examples created for this project. Their names, addresses and stories are invented, so please do not try to book them. Always confirm details with a restaurant before you visit.
How it is built
BonAppé Find uses Vue for the interface, Node.js and Express for the API, and MongoDB Atlas for the cloud database. The design was created in Figma.
The team
Abygale Santos and Ayenne Wage designed the experience in Figma. Prince Pangilinan built the backend and the frontend. Casey Ong wrote and finalized the documentation, checked every deliverable and manages the repository. Meet everyone on the Team page.

readTimeMinutes | 2
tags | grades, score, quality
body | Every restaurant in BonAppé Find carries a list of grades. Each entry has three parts: a date, a letter grade and a score. The letter (A, B, C or Z) is the label recorded on that date. The score is the number of points recorded with it. On a restaurant profile you will see every entry in a table.

The Quality Score is simple: we add up all of the scores for a restaurant. A restaurant with several strong entries builds a higher total, and any restaurant above 90 points appears on the Best Quality page.

Keep two things in mind. First, totals grow as more grades are recorded, so also look at the Grades recorded column. Second, grades describe the records in our database, not a promise about your meal. Use them as a starting point, then read the story and the country guide.

tags | tipping, etiquette, travel
body | Tipping customs can feel confusing, so here is a simple overview. Remember to check the bill first, because a service charge may already be included.

United States: 15 to 20 percent is typical in sit-down restaurants. Mexico: 10 to 15 percent. Philippines: a 10 percent service charge is often added; if not, 5 to 10 percent is appreciated. India: 5 to 10 percent if no service charge is added. Italy: a cover charge (coperto) is common, and a few extra euros for great service is plenty. France: service is included by law, so a small extra is optional. Thailand: not required, but rounding up is appreciated. Japan: do not tip; it can cause confusion, and a polite thank you is best.

When in doubt, ask the staff or follow what locals do.

# BonAppé Find
 
> Great dining starts with a great find.
 
BonAppé Find is a full-stack restaurant and country discovery web app built for the
6ADDBASE Final Project: Restaurants. It reads restaurants from a MongoDB Atlas
database named dbRestaurants and lets people search, filter, rank, add, edit and
delete them. Curated profiles and country guides explain dishes, dining etiquette,
tipping and food festivals.
 
## Features
 
- Search by restaurant name or cuisine
- Filter and group by borough, region or country
- Best Quality page: aggregate of total score greater than 90
- Add, edit and delete restaurants, saved to MongoDB Atlas
- Restaurant profiles and eight country food guides
- Insights, compare, saved list, reviews, newsletter and contact form
 
## Tech
 
- Frontend: Vue 3, Vite, Vue Router, Pinia, Axios
- Backend: Node.js 20, Express 4, Mongoose 8
- Database: MongoDB Atlas (dbRestaurants)
- Design: Figma, palette and tokens in design/tokens.css
 
## Getting started
 
1. Clone the repository and open the folder: cd bonappe-find
2. Copy server/.env.example to server/.env and add your MongoDB Atlas URI
3. Copy client/.env.example to client/.env
4. Install dependencies in client and server
5. Import the course data, then seed the static content
6. Start the API and the client, then open http://localhost:5173

6.2 The Language-Neutral Contract
Rule | What every stack must do
Database | MongoDB Atlas, database dbRestaurants, collection restaurants plus the collections in Part 3.4. Copy field names exactly, for example restaurant_id, countrySlug and profile.signatureDishes.
Base path | Every route starts with /api. Fixed paths such as /random, /meta/filters, /compare and /stats/... are matched before /:id.
Success response | { "success": true, "data": ..., "meta": ... } with status 200, or 201 for a created record.
Error response | { "success": false, "message": "...", "errors": [ { "field": "...", "message": "..." } ] }
Status codes | 400 bad id, 401 not logged in, 403 not allowed, 404 not found, 409 duplicate, 422 validation failed, 429 too many requests, 500 server error.
Validation | Use the exact messages from Part 5 (Add and Edit validation table, Contact and Login pages). Validate on the server even if the client also validates.
Dates and numbers | Dates are ISO 8601 strings in JSON, for example 2026-02-08. Scores are numbers from 0 to 200. Pagination uses page (default 1) and limit (default 20, maximum 100).
Quality Score | The sum of grades.score per restaurant. Best Quality keeps totals greater than TOP_QUALITY_MIN (default 90) and sorts from high to low.
Configuration | Read PORT, MONGODB_URI, CLIENT_ORIGIN, JWT_SECRET, JWT_EXPIRES_IN, TOP_QUALITY_MIN, REQUIRE_AUTH_FOR_WRITES and ADMIN_EMAILS from environment variables (Part 3.7). Never commit secrets.
Security | Allow only the client origin (CORS), send security headers and rate-limit the contact and login routes. Hash passwords with bcrypt or Argon2 and sign tokens with the secret from the environment.

6.5 Key Queries in Any Language
MongoDB pipelines are plain data, so the same stages work in every language. Test a pipeline in MongoDB Compass or mongosh first, then copy it into your code.
Best Quality (aggregate), language-neutral form for mongosh or Compass
db.restaurants.aggregate([
  { $match: {} },
  { $unwind: "$grades" },
  { $group: {
      _id: "$_id",
      name: { $first: "$name" },
      borough: { $first: "$borough" },
      cuisine: { $first: "$cuisine" },
      country: { $first: "$country" },
      totalScore: { $sum: "$grades.score" },
      gradeCount: { $sum: 1 }
  } },
  { $match: { totalScore: { $gt: 90 } } },
  { $sort: { totalScore: -1, name: 1 } },
  { $limit: 50 }
])
Group by borough, language-neutral form
db.restaurants.aggregate([
  { $group: { _id: "$borough", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
])
Search by name, cuisine or both
// name
{ name: { $regex: "<escaped keyword>", $options: "i" } }
// cuisine
{ cuisine: { $regex: "<escaped keyword>", $options: "i" } }
// all
{ $or: [
    { name: { $regex: "<escaped keyword>", $options: "i" } },
    { cuisine: { $regex: "<escaped keyword>", $options: "i" } }
] }
Always escape regular-expression characters in the keyword (re.escape in Python, preg_quote in PHP, Regex.Escape in C#, Pattern.quote in Java, a small escape helper in JavaScript) so a search such as C++ cannot break the query.
Node.js (Mongoose)
const results = await Restaurant.aggregate([
  { $match: filters },
  { $unwind: "$grades" },
  { $group: {
      _id: "$_id",
      name: { $first: "$name" }, borough: { $first: "$borough" },
      cuisine: { $first: "$cuisine" }, country: { $first: "$country" },
      totalScore: { $sum: "$grades.score" }, gradeCount: { $sum: 1 } } },
  { $match: { totalScore: { $gt: min } } },
  { $sort: { totalScore: -1, name: 1 } },
  { $limit: limit },
]);
Python (PyMongo)
pipeline = [
    {"$match": filters},
    {"$unwind": "$grades"},
    {"$group": {
        "_id": "$_id",
        "name": {"$first": "$name"}, "borough": {"$first": "$borough"},
        "cuisine": {"$first": "$cuisine"}, "country": {"$first": "$country"},
        "totalScore": {"$sum": "$grades.score"}, "gradeCount": {"$sum": 1}}},
    {"$match": {"totalScore": {"$gt": min_score}}},
    {"$sort": {"totalScore": -1, "name": 1}},
    {"$limit": limit},
]
results = list(db["restaurants"].aggregate(pipeline))
PHP (mongodb/mongodb)
$pipeline = [
    ['$match' => (object) $filters],
    ['$unwind' => '$grades'],
    ['$group' => [
        '_id' => '$_id',
        'name' => ['$first' => '$name'], 'borough' => ['$first' => '$borough'],
        'cuisine' => ['$first' => '$cuisine'], 'country' => ['$first' => '$country'],
        'totalScore' => ['$sum' => '$grades.score'], 'gradeCount' => ['$sum' => 1]]],
    ['$match' => ['totalScore' => ['$gt' => $min]]],
    ['$sort' => ['totalScore' => -1, 'name' => 1]],
    ['$limit' => $limit],
];
$results = $collection->aggregate($pipeline)->toArray();
C# (MongoDB.Driver)
var pipeline = new[]
{
    new BsonDocument("$match", filters),
    new BsonDocument("$unwind", "$grades"),
    BsonDocument.Parse(@"{ $group: { _id: '$_id', name: { $first: '$name' },
        borough: { $first: '$borough' }, cuisine: { $first: '$cuisine' },
        country: { $first: '$country' }, totalScore: { $sum: '$grades.score' },
        gradeCount: { $sum: 1 } } }"),
    new BsonDocument("$match", new BsonDocument("totalScore", new BsonDocument("$gt", min))),
    new BsonDocument("$sort", new BsonDocument { { "totalScore", -1 }, { "name", 1 } }),
    new BsonDocument("$limit", limit)
};
var results = await collection.Aggregate<BsonDocument>(pipeline).ToListAsync();
Java (Spring Data MongoDB)
Aggregation agg = Aggregation.newAggregation(
    Aggregation.unwind("grades"),
    Aggregation.group("_id")
        .first("name").as("name").first("borough").as("borough")
        .first("cuisine").as("cuisine").first("country").as("country")
        .sum("grades.score").as("totalScore").count().as("gradeCount"),
    Aggregation.match(Criteria.where("totalScore").gt(min)),
    Aggregation.sort(Sort.by(Sort.Direction.DESC, "totalScore")
        .and(Sort.by(Sort.Direction.ASC, "name"))),
    Aggregation.limit(limit));
AggregationResults<Document> results =
    mongoTemplate.aggregate(agg, "restaurants", Document.class);
The optional filter stage is left out of the Java example for brevity; add a match stage first when a country or cuisine filter is needed. Library method names can change between versions, so check the current driver documentation if a call does not compile.

  "cuisine": "Filipino",

  "borough": "Pampanga",
  "city": "San Fernando",

    "signatureDishes": ["Sizzling sisig", "Sinigang na baboy", "Turon with langka"],

    "openingHours": "Daily, 10:00 to 21:00",

Leave out --jsonArray when the file has one JSON object per line.
